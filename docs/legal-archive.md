# Архив договорного БП на существующем сервисе

Архив работает отдельным модулем в существующем Node-сервисе и не требует нового
сервиса Render, диска или базы данных Render. Файлы и журнал остаются в Bitrix24.
Дополнительная фиксированная подписка не создаётся; используются доступное место
Bitrix24, REST-лимиты и включённый трафик/ресурсы существующего сервиса Render.

## Поведение

Модуль опрашивает только разрабатываемый RPA №57. Он сохраняет проекты юриста,
подготовленные договоры, счета, акты и финальные файлы. При согласовании делает
отдельную копию документа, скачивает её обратно и проверяет SHA-256 перед записью
ключа готовности версии. Фактические согласования и переходы выполняются БП, а
не модулем архива. Email менеджера берётся из профиля автора заявки.

AI, отправки email/ЭДО, подписи, разрешения на выпуск и новые публичные HTTP
маршруты не добавляются. Штатный скоринг и расчёт трудозатрат сохраняются.
При выключенном флаге архив не выполняет сетевых запросов. Некорректная
конфигурация архива фиксируется безопасным кодом и не мешает запуску CRM-сервиса.

## Хранение и восстановление

В выделенной папке личного Диска служебной учётной записи находятся папки заявок:

- `blob-<sha>-<имя>` — неизменяемый исходный файл;
- `source-<поле>-<id>.json` — исходный ID, хеш, контекст и дата наблюдения;
- `history-<поле>-<id>.json` — связь исходника с копией в истории RPA;
- `checkpoint-<поле>-<hash>.json` — версия и ID проверенных согласуемых копий.

Существующий объект с тем же именем проверяется по содержимому; он не
перезаписывается. Неудачный/потерянный ответ загрузки обрабатывается повторным
чтением Bitrix24. После полного удаления памяти процесса новый экземпляр
восстанавливает состояние из этих объектов, без SQLite или локального кеша.
При испорченном архиве/копии ключ готовности не публикуется.

Файл `legal-archive-worker-lease.json` с уникальным именем координирует старый и
новый экземпляры при развёртывании Render. Второй экземпляр ждёт. Действующий
обработчик продлевает lease; после сбоя истёкший lease можно занять заново.
Только собственный или истёкший файл блокировки переносится в восстанавливаемую
корзину. Документы и записи версий модуль не удаляет.

Права папки не расширяются. Не включайте публичные ссылки. Не публикуйте архив,
журнал, договорные данные, содержимое `.env` или ключ подключения в репозитории.

## Подключение

Существующие build/start-команды Render и тариф сохраняются. Архив выключен
по умолчанию. До его включения нужны доступы текущего подключения `rpa`, `disk`,
`user_basic` и уже подготовленные служебные поля RPA №57.

Переменные добавляются только в Environment существующего сервиса Render:

```dotenv
LEGAL_ARCHIVE_ENABLED=false
LEGAL_ARCHIVE_WEBHOOK_URL=<секрет текущего разрешённого REST-подключения>
LEGAL_ARCHIVE_FOLDER_ID=<ID проверенной выделенной папки>
LEGAL_ARCHIVE_ALLOWED_ITEM_IDS=19
LEGAL_ARCHIVE_POLL_MS=60000
```

1. Выполнить `npm install` и `npm test`. Проверить предлагаемый diff.
2. После разрешения на применение влить подготовленную ветку. Сервис Render
   следит за `main` и начнёт deploy; конфигурация архива всё ещё выключена.
3. Проверить конкретный deploy до `live` и ответ `/health`. Убедиться, что скоринг
   продолжает обрабатывать прежние входы.
4. Настроить секрет и проверенный ID папки. Включить `LEGAL_ARCHIVE_ENABLED=true`
   только с `LEGAL_ARCHIVE_ALLOWED_ITEM_IDS=19` для вымышленного теста.
5. Проверить логи компонента `legal_archive`, копию и архив, повтор после
   перезапуска, отсутствие дублей и сохранность старых записей.
6. Снимать ограничение на тестовую заявку только после сквозной приёмки
   нативных ролей, маршрутов и проверок версий в RPA.

Отключение: установить `LEGAL_ARCHIVE_ENABLED=false` и выполнить deploy
конфигурации. Архивные объекты в Bitrix24 сохраняются. Возврат к предыдущему
коммиту не должен удалять эти объекты. Секрет архива отдельный от переменной
существующего CRM-обработчика; менять его `BITRIX24_WEBHOOK_URL` не требуется.

## Ограничения

Опрос не восстанавливает файл, заменённый до его первого наблюдения. Согласования
должны ждать готовой версии и проверять её соответствие текущему исходнику.
Сам по себе модуль не заменяет эти нативные блокировки. Ограничение скачивания —
20 МиБ на файл. Адреса скачивания проверяются, неизвестные хосты/редиректы
блокируются; ошибка не выводит секретные URL и содержимое документов в лог.

REST RPA не предоставляет атомарного compare-and-swap для полей заявки.
Проверки снимка до/после копирования выявляют изменения во время обработки;
блокировка предотвращает одновременную запись двух обработчиков. Нативная
проверка исходного ID и ключа остаётся обязательной непосредственно перед
переходом/согласованием. Администраторское ручное редактирование архивных полей
не считается допустимым рабочим сценарием и может потребовать восстановления.
